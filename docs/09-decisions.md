# 09. 설계 결정 기록

결정마다 맥락, 결정, 결과(대가)를 짧게 적는다. 결정을 바꿀 때는 이 파일에 새 항목을 추가하고,
이전 항목은 지우지 않고 상태를 "대체됨 → D-0xx"로 바꾼다.

### D-001 Asterisk 22 LTS를 Docker에서 소스로 빌드한다 — 채택

- **맥락**: 회사 IPCC는 오픈소스 Asterisk 기반이다. 실무에서는 소스 빌드가 흔하고, 어떤 모듈이 들어가는지 알아야 한다.
  개발 장비는 Apple Silicon Mac이다.
- **결정**: `debian:bookworm-slim`에서 22.11.0을 소스 빌드한다. `menuselect`로 BUILD_NATIVE를 끄고 ulaw 사운드를 받는다.
  sngrep, tcpdump, sipp를 같이 넣고 빌드 트리(`/usr/src/asterisk`)를 남겨 소스를 읽을 수 있게 한다.
- **결과**: 첫 빌드에 몇 분 걸리고 이미지가 크다. 회사 버전이 다르면 `ASTERISK_VERSION`으로 맞출 수 있다.
  단, 18 이하라면 chan_sip을 쓰고 있을 수 있으니 입사 후 버전부터 확인한다.

### D-002 SIP는 PJSIP만 쓴다 — 채택

- **맥락**: chan_sip(`sip.conf`)은 Asterisk 21에서 삭제됐다. 인터넷 예제의 상당수가 아직 chan_sip이다.
- **결정**: `pjsip.conf`(chan_pjsip)만 쓰고 템플릿(`(!)`)으로 내선 설정을 묶는다.
- **결과**: 블로그 예제를 옮길 때 옵션 이름을 PJSIP 식으로 바꿔야 한다.

### D-003 Mac Docker Desktop의 NAT는 `local_net` + `EXTERNAL_IP` 템플릿으로 푼다 — 대체됨 → D-014

> `local_net = 127.0.0.1/32`만 둔 부분이 틀렸다. 컨테이너 자신의 주소가 local_net 밖이면 Asterisk는 SDP 주소를
> 바꿔 적지 않는다. 아래는 당시 기록이다.

- **맥락**: Mac은 컨테이너 IP로 직접 갈 수 없다. 포트포워딩을 거친 패킷은 컨테이너 안에서 출발지가 172.23.0.1로 보인다.
- **결정**: `local_net = 127.0.0.1/32`로 컨테이너 밖을 모두 '바깥'으로 보고, `external_*_address`에 `EXTERNAL_IP`를 넣는다.
  `EXTERNAL_IP`는 실행 환경마다 달라서 `entrypoint.sh`가 템플릿에서 설정 파일을 만든다. RTP는 10000-10099만 쓰고 그만큼만 공개한다.
- **대안**: Docker host 네트워크(Docker Desktop에서는 지원이 제한적), Linux VM(OrbStack, UTM — 더 현실적이지만 설치 부담).
- **결과**: 동시 약 25통화로 제한된다. 부하 테스트(Stage 6)에서는 범위를 넓히고 compose 포트도 같이 바꿔야 한다.

### D-004 AMI 클라이언트는 표준 라이브러리만으로 직접 구현한다 — 채택

- **맥락**: 회사 핵심 엔진의 바닥이 AMI 연동이다. Go AMI 라이브러리는 여럿 있지만 재접속·재동기화·느린 소비자 처리 방식이 제각각이다.
- **결정**: `net`, `bufio`, `log/slog`만 써서 `engine/ami`를 만든다.
- **결과**: 코드를 끝까지 이해하고 Rust 구현과 1:1로 비교할 수 있다. 기능은 필요한 만큼만 있다.

### D-005 연결 상태를 이벤트와 같은 채널로 보내고, 로그인은 동기로 처리한다 — 채택

- **맥락**: 소비자는 "어디까지가 끊기기 전 이벤트인지", "재동기화를 언제 할지"를 알아야 한다.
- **결정**: `Connected`/`Disconnected`를 AMI 이벤트와 같은 `Events()` 채널로 보낸다. 로그인은 읽기 루프를 띄우기 전에 동기로 해서
  `Connected`가 그 연결의 어떤 이벤트보다 먼저 나가게 한다.
- **결과**: 소비자는 순서만 따라가면 된다. (`TestConnectedComesFirstThenEventsInOrder`)

### D-006 읽기 루프와 소비자 사이에 무제한 큐를 둔다 — 채택

- **맥락**: 읽기 루프가 막히면 Asterisk가 `writetimeout`(기본 100ms)을 넘긴 세션을 느린 클라이언트로 보고 끊는다. 이벤트 유실은 상태 오류로 이어진다.
- **결정**: `pump`가 소비자 속도와 관계없이 이벤트를 받아 쌓는다. 적체는 `QueueDepth()`로 본다.
- **결과**: 소비자가 계속 느리면 메모리가 는다. 적체 경보가 필요하다 (Stage 1 과제).

### D-007 받은 원본 바이트를 녹화한다 (로그인에 성공한 연결만) — 채택

- **맥락**: 이벤트 해석·상태머신·포팅을 검증하려면 같은 입력을 몇 번이고 다시 넣을 수 있어야 한다.
- **결정**: 받은 바이트를 그대로 파일로 남긴다. 보낸 액션(Secret 포함)은 남기지 않는다.
  재접속 시도마다 빈 파일이 생기던 문제를 고쳐서, 로그인 전 바이트는 메모리에 모았다가 성공하면 파일에 쓴다.
- **결과**: 녹화에는 고객 전화번호가 들어간다. `recordings/`는 git에서 제외하고, 테스트 데이터는 가린 뒤 옮긴다.

### D-008 상담원 업무 상태는 엔진이 소유한다 — 채택 (race는 검증 필요)

- **맥락**: 이석·후처리는 Asterisk에 없는 개념이다. Asterisk에도 맡기면(wrapuptime, autopause) 두 곳이 상태를 따로 바꿔 어긋난다.
- **결정**: `queues.conf`에서 `wrapuptime = 0`, `autopause = no`, `persistentmembers = no`. 엔진이 `QueueAdd`/`QueuePause`로만 반영한다.
- **결과**: Asterisk 재시작 뒤 엔진이 멤버를 다시 넣어야 한다 (실측 확인). 후처리 진입 직후의 race는 06 문서 9절의 가설로 남겨 두고
  Stage 2에서 녹화로 확인한다. 필요하면 짧은 `wrapuptime`을 안전장치로 둔다.

### D-009 시뮬레이션은 Local 채널로 한다 — 채택

- **맥락**: 엔진을 개발할 때마다 소프트폰으로 직접 통화할 수는 없다. 에이전트도 스스로 콜을 만들 수 있어야 한다.
- **결정**: `[sim]`(가짜 고객), `[sim-agent]`(가짜 상담원 단말)을 다이얼플랜에 두고 `Originate`·`QueueAdd`로 부른다.
  SIP 경로는 SIPp(테스트 전용 내선 9001, 컨테이너 안)로 따로 검증한다.
- **결과**: Local 채널 쌍(`;1`/`;2`) 때문에 이벤트가 실제 SIP 콜보다 많다. 실제 상담원 흐름은 소프트폰 녹화로 따로 확인해야 한다.

### D-010 시작 로그의 WARNING/ERROR를 0으로 유지한다 — 채택

- **맥락**: 평소 로그에 ERROR가 수십 줄이면 진짜 문제를 놓친다.
- **결정**: 쓰지 않는 모듈은 `noload`, 나중 Stage에서 쓸 모듈은 주석과 함께 `noload`, 꼭 있어야 하는 코어 설정은 빈 파일로 둔다.
- **결과**: 설정 파일 수가 늘었다. 모듈을 다시 켤 때는 `modules.conf`의 해당 줄을 지우고 설정을 추가한다.

### D-011 상태머신 코어는 I/O 없는 함수로 만든다 — 채택 (Stage 2에서 확정 → D-016)

- **맥락**: replay 테스트와 Rust↔Go 차분 테스트를 하려면 같은 입력에 같은 출력이 나와야 한다.
- **제안**: `Apply(state, input, now) → effects`. 효과 실행은 바깥 껍데기가 한다 (06 문서 2절).
- **확정**: `Engine.Apply(ts, input) → 출력 줄`. 시각은 입력에 붙여 넘기고, 타이머는 코어 안에서 마감 시각으로 처리한다.

### D-012 e2e는 실제 Asterisk에 붙는 Go 테스트로, 이벤트가 올 때까지 기다리며 검증한다 — 채택

- **맥락**: 통합 검증을 사람이 로그를 눈으로 보며 했다. 에이전트가 스스로 "만들고 → 돌리고 → 검증"하려면
  명령 하나가 성공/실패를 내야 한다.
- **결정**: `engine/e2e`에 `e2e` 빌드 태그가 붙은 Go 테스트를 둔다. 엔진과 같은 `ami.Client`로 접속해 액션을 보내고,
  고정된 sleep 대신 기대한 이벤트가 모일 때까지 기다린다. 실제 상담원·통화가 있으면 시작하지 않는다.
  콜 종료(AgentComplete)는 고객번호가 아니라 상담원 기준으로 짝짓는다 (05 문서 6절 11번).
- **결과**: `make e2e` 약 30초. 실행 몇 번에 한 번 나타나는 Asterisk 동작(채널 정보 없는 AgentComplete)을
  이 테스트가 처음 드러냈다. 처음 버전은 고객번호로 짝지어서 가끔 실패했다.

### D-013 CI는 로컬과 같은 make 명령을 쓰고, Asterisk 이미지는 Actions 캐시에 둔다 — 채택

- **맥락**: "로컬에서는 되는데 CI에서는 안 된다"를 줄이려면 같은 명령을 써야 한다. Asterisk 소스 빌드는 몇 분 걸린다.
- **결정**: `go` 작업(`make test` + golangci-lint)과 `e2e` 작업(buildx로 이미지 빌드 + `make e2e`, `E2E_RESTART=1`)으로 나눈다.
  이미지 레이어는 `type=gha` 캐시에 두고, 태그를 compose의 image와 맞춰 `make e2e`가 다시 빌드하지 않게 한다.
  golangci-lint 버전은 Makefile과 워크플로에서 같게 고정한다. 변경은 브랜치 → PR → CI 통과 → 병합 순서로 들어간다.
- **결과**: 첫 실행은 이미지를 빌드하느라 오래 걸리고, 이후에는 캐시를 쓴다.
  Asterisk 버전을 바꿀 때는 Dockerfile·docker-compose.yml·워크플로의 `ASTERISK_VERSION`을 같이 바꾼다.

### D-014 `local_net`에는 컨테이너 자신과 127.0.0.1만 넣고, 컨테이너 IP는 시작할 때 찾는다 — 채택 (D-003 대체)

- **맥락**: Mac에서 실제로 걸어 본 `make rtp-check`가 SDP에 `c=172.23.0.2`(컨테이너 IP)가 적히는 것을 보여 줬다.
  Mac은 그 주소로 갈 수 없어서 소프트폰은 "연결은 되는데 소리가 안 들림"이 됐을 것이다.
  컨테이너 안에서 도는 SIPp 테스트는 이 길을 지나지 않아서 통과했다.
  Asterisk 소스를 확인하니, 받는 쪽이 local_net **밖**이고 **자기 SDP 주소가 local_net 안**일 때만 external 주소로 바꿔 적는다.
- **결정**: `local_net = 127.0.0.1/32`와 `local_net = <컨테이너 IP>/32`. 컨테이너 IP는 `entrypoint.sh`가 `hostname -i`로 찾아
  템플릿에 넣는다. Mac의 패킷이 보이는 Docker 게이트웨이(172.x.0.1)는 일부러 local_net 밖에 둔다.
- **대안**: compose 네트워크 대역과 컨테이너 IP를 고정하기 (다른 Docker 네트워크·VPN과 겹칠 위험), 대역 전체를 local_net에
  넣기 (게이트웨이까지 들어가서 조건이 깨진다).
- **결과**: Mac에서 RTP 100개 중 96개가 돌아온다(나머지는 strictrtp 학습 중 버림). 같은 Compose 네트워크의 다른 컨테이너가
  SIP 단말이 되면 그쪽에도 EXTERNAL_IP가 적히므로, 그런 구성을 만들 때 다시 본다.
  e2e의 RTP 단계와 CI가 이 회귀를 계속 지킨다.

### D-015 사람 없이 쓰는 테스트 장치: 9002(고정 주소 상담원 전화기), 602(순수 에코), rtpcheck — 채택

- **맥락**: 소프트폰으로만 확인할 수 있던 두 가지가 남아 있었다. 실제 SIP 상담원 흐름, 그리고 Mac에서 오가는 음성 경로다.
- **결정**:
  - 9002는 등록 없이 `contact = sip:9002@127.0.0.1:5072`로 부른다. 그 포트에서 SIPp(`uas-agent.xml`)가 받고 먼저 끊는다.
    소프트폰 계정(1001~1003)을 건드리지 않고, OPTIONS에 답하지 못하는 SIPp를 위해 `qualify_frequency = 0`.
  - 602는 안내멘트 없이 바로 Echo()라서 RTP 왕복을 바로 셀 수 있다.
  - Mac에 SIPp를 설치하는 대신 Go로 최소 SIP UA(`engine/rtpcheck`)를 만들었다. 의존성 없이 Mac과 CI 러너에서 똑같이 돌고,
    SIP·SDP·RTP를 코드로 읽을 수 있는 학습 자료도 된다.
- **결과**: `make sip-agent-call`, `make rtp-check`, 그리고 e2e의 두 단계. 소프트폰으로 실제 소리를 듣는 확인은 여전히 사람 몫이다.

### D-016 상태머신의 기준 구현은 Rust 레거시이고, Go는 바이트 단위로 같은 출력을 내야 한다 — 채택

- **맥락**: 입사 후 업무(Rust 엔진 → Go)를 미리 연습한다. "같다"를 사람이 눈으로 판단하면 포팅이 끝나지 않는다.
- **결정**: 두 구현이 같은 CLI(`replay [--cmds F] 녹화…`)와 같은 출력 계약(07 문서 4절)을 갖는다.
  기대 출력(`*.golden.jsonl`)은 **Rust로만** 만든다(`make golden`). Go 테스트에는 `-update` 플래그를 두지 않는다.
  `make diff-test`가 모든 녹화에서 Rust 출력 = Go 출력 = 기대 출력을 확인하고 CI(`rust` 작업)가 PR마다 돌린다.
  명세가 바뀌면 Rust를 먼저 고치고 → 기대 출력 → Go 순서로 반영한다.
- **결과**: 첫 차분 테스트에서 0 diff. 이후 레거시 파서 버그 1건을 이 하네스로 고정했다 (07 문서 10절).
  레거시를 고칠 수 없는 실무라면 '알려진 차이 목록'을 두는 방식으로 바꾼다.

### D-017 Rust는 Docker 이미지로만 빌드하고, 외부 crate를 쓰지 않는다 — 채택

- **맥락**: 학습자 Mac과 CI 러너에 Rust 툴체인을 설치·관리하지 않고 같은 버전으로 돌리고 싶다.
- **결정**: `rust:1.98.1-slim-bookworm` 이미지로 `cargo test`/`cargo build`를 돌린다. 저장소는 읽기 전용으로 마운트하고
  빌드 산출물·레지스트리는 이름 있는 볼륨(`ipcc-cargo-target`, `ipcc-cargo-registry`)에 둔다. `Cargo.lock`은 커밋한다.
  Go 쪽과 같은 조건(표준 라이브러리만)으로 맞춰서, JSON도 직접 쓴다.
- **결과**: 첫 실행은 이미지를 받느라 느리다. serde·tokio 같은 실무 crate 경험은 이 저장소로는 얻지 못한다.

### D-018 재동기화는 FullyBooted 뒤에, 스냅샷은 이벤트 스트림 안에서 받는다 — 채택

- **맥락**: (1) Asterisk 재시작 직후 엔진이 붙으면 `QueueStatus`가 `Invalid/unknown command`로 실패했다 (e2e에서 발견).
  (2) `SendList`는 목록을 따로 모아 주므로 스냅샷과 실시간 이벤트의 앞뒤를 잃고, 이미 끊긴 채널이 스냅샷으로 되살아날 수 있다.
- **결정**: (1) `Connected`가 아니라 `FullyBooted`를 받으면 재동기화한다. (2) `ami.Client.SendListInline`을 추가해 응답·항목·Complete를
  받은 순서 그대로 `Events()`로 흘리고, 녹화 재생과 같은 `state.Grouper`가 Complete 자리에서 스냅샷 입력으로 묶는다.
- **대안**: 스냅샷을 받는 동안 이벤트를 버퍼에 쌓았다가 스냅샷 뒤에 적용하기 (멱등하지 않은 이벤트는 두 번 반영된다).
- **결과**: 실시간과 재생의 처리 순서가 같다. AMI 사용자에게 `system` 클래스 읽기 권한이 없으면 FullyBooted가 오지 않아
  재동기화가 일어나지 않는다 (manager.conf의 `read`에 넣어 둔다).

### D-019 상담원 정책 기본값 — 채택

- **결정**: 로그인 직후 NotReady(로그인). 후처리 10초가 지나면 자동 대기. 무응답 2회 연속이면 자동 이석(무응답).
  통화·벨 중에 누른 이석은 예약하고 끝나는 순간 적용한다. 벨 중에 고객이 끊은 것은 무응답으로 세지 않는다.
  엔진이 모르는 큐 멤버는 지우지 않고 Asterisk 상태를 받아들인다(`resync_adopt`). 액션이 실패하면 로그만 남기고 다음 재동기화가 고친다.
- **결과**: 값은 `state.Policy`와 `bin/engine -acw -max-missed`로 바꾼다. 센터마다 다른 정책(모르는 멤버 제거, 후처리 상한 등)은
  입사 후 실제 요구를 보고 정한다. D-008의 '후처리 직후 race'는 아직 녹화로 확인하지 않았다 (06 문서 9절 5번).

### D-020 첫 화면은 Next.js, 게이트웨이는 라우트 핸들러, 엔진 → 화면은 SSE — 채택

- **맥락**: 상태머신을 화면으로 보고 싶다는 요청. Stage 3 계획은 Redis + Node.js 게이트웨이(WebSocket)였다.
  지금은 엔진 하나, 화면 하나이고 데이터는 거의 서버 → 화면 한 방향이다.
- **결정**: 엔진(`bin/engine -http`)이 SSE를 낸다. 접속하면 전체 상태를 actor 안에서 만들고 구독을 등록한 뒤 바뀐 줄만 보낸다.
  Next.js(`web/`)의 라우트 핸들러가 그 SSE를 브라우저에 이어 주고 명령을 넘긴다(게이트웨이). 화면용 값(상태 시각, 누적 결과)은
  상태머신 코어가 아니라 껍데기(`live/view.go`)가 모은다(D-016의 출력 계약을 지키려고). 엔진 API와 개발 서버는 127.0.0.1에만 연다.
- **대안**: Redis pub/sub + 별도 Node 게이트웨이 + WebSocket (구성 요소 셋이 늘고, 지금 규모에서는 얻는 것이 없다),
  브라우저가 엔진에 직접 붙기 (엔진 주소·CORS가 화면에 새고, 나중에 인증을 넣을 자리가 없다).
- **결과**: `make engine` + `make web` 두 개로 돈다. 게이트웨이를 여러 대 띄우거나 엔진 재시작과 화면 연결을 떼어 놓으려면
  그때 Redis를 넣는다. 화면 배치(떠 있는 아이콘 레일, 유리 패널, 요약 카드 → 항목 카드 → 표 → 로그)는 흔한 운영 포탈 구조를 따랐다.

### D-021 app_queue 없이 직접 만든 큐(룸 큐)를 별도 패키지로 둔다 — 채택

- **맥락**: app_queue에 분배를 맡기는 구조(Stage 2)만 알면, 큐를 직접 만드는 실무 구조(엔진이 분배, 통화별 회의방,
  두 축 상태)를 다룰 때 감이 없다. 두 구조의 장단점을 직접 비교해 보고 싶다.
- **결정**: `engine/rq`(코어 + Runner)와 `bin/rqengine`을 새로 만든다. 고객은 `rq-<Linkedid>` 회의방에서 기다리고,
  엔진이 AMI Originate로 상담원을 같은 방에 부른다. dialplan은 UserEvent 5종으로 사실만 알린다.
  상담원 상태는 업무 모드 × 통화 단계 두 축. Stage 2 엔진(`engine/state`, Rust 출력 계약)은 그대로 두고 대체하지 않는다.
  이번 과제는 포팅 연습이 아니라서 Rust 레거시는 두지 않는다.
- **대안**: `engine/state`를 두 축으로 바꾸기 (Rust → 기대 출력 → Go 순서의 큰 변경이고, app_queue 구조와의 비교 대상이 사라진다).
- **결과**: 대표번호 5100이 룸 큐, 5000이 app_queue 큐로 공존한다. 엔진이 죽으면 룸 큐는 분배가 멈춘다(app_queue는 계속한다).
  재시작 시 방 재동기화, 보류, 협의 전환은 남은 과제(12 문서 8절). `app_confbridge`를 켜고 `confbridge.conf`를 추가했다.
  → 재동기화·보류·협의·벨 취소·스킬·녹음·화면은 D-022, D-023으로 이어서 했다.

### D-022 룸 큐 재시작: 업무 상태는 엔진 저장소, 통화 상태는 채널 목록 — 채택

- **맥락**: 룸 큐는 엔진이 상태를 다 갖는다. 엔진이 다시 시작하면 무엇을 어디서 되찾을지 정해야 한다.
- **결정**: 업무 상태(로그인·모드·사유·스킬·후처리 끝 시각)는 엔진이 바뀔 때마다 파일(`-state`)에 저장하고 시작할 때 되살린다
  (기준이 엔진이므로, D-008). 통화 상태는 `FullyBooted` 뒤 `CoreShowChannels` 한 번으로 다시 읽는다 (교환기가 기준).
  이를 위해 방 이름에 큐를 넣고(`rq-<큐>-<Linkedid>`), Originate에 `ChannelId`(`<방>-a<시각>`)를 붙여 벨 울리는 채널도 알아본다.
  재동기화를 마치기 전에는 분배하지 않는다. 파일 쓰기는 별도 고루틴에서, 밀리면 마지막 것만 쓴다.
- **대안**: (1) ConfbridgeListRooms → 방마다 ConfbridgeList — 왕복이 방 수만큼이고 벨 울리는 채널은 안 보인다.
  (2) AstDB(`DBPut`)에 업무 상태 저장 — 교환기와 엔진이 같이 죽는 경우를 못 견디고, 실무의 DB 위치와도 다르다.
  (3) `manager.conf`의 `channelvars`로 RQ_* 변수를 모든 이벤트에 싣기 — Stage 2 녹화·이벤트 사전까지 모양이 바뀐다.
- **결과**: 진행 중인 의도(보류·협의·전환 요청)는 되살리지 못한다 (12 문서 5절). ChannelId 덕분에 벨 취소와
  "이미 끊은 벨의 늦은 실패 응답" 구분도 정확해졌다.

### D-023 보류는 고객만 보류 방으로 옮긴다 (협의 전환도 이것으로) — 채택

- **맥락**: 회의방 구조에서 "고객만 대기음, 상담원은 말할 수 없게"를 만들어야 한다. 협의 전환은 고객이 듣지 못하는 곳에서 상담원 둘이 먼저 통화해야 한다.
- **결정**: 엔진이 고객 채널을 `Redirect`로 `[rq-hold]`(혼자 있는 보류 방 `<방>-hold`, 대기음)로 보내고, 해제는 `[rq-back]`으로 원래 방에 돌려보낸다.
  상담원은 원래 방에 남으므로, 그 방에 다른 상담원을 부르면 협의가 된다: 완료 = 원래 상담원을 빼고 해제, 취소 = 넘겨받을 상담원을 빼고 해제,
  해제만 하면 3자통화. 보류 중 상담원이 나가면 무조건 해제한다(남은 상담원과 잇거나 다시 대기열).
- **대안**: (1) `ConfbridgeMute` + 고객에게 대기음 — 고객은 여전히 상담원 말을 듣는다. (2) 상담원을 다른 방으로 — `end_marked`라서 고객이 같이 나간다.
- **결과**: Redirect는 끊김 처리기를 부르지 않는다(05 문서 27). 상태는 dialplan의 RQHold/RQUnhold로 확인한다.
  현황판은 `/rooms` 페이지로 따로 두고 게이트웨이를 `/api/rq/*`로 나눴다 (같은 셸, 엔진만 다르다).
